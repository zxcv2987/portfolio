# 사내 이슈 관리 시스템을 요구사항부터 풀스택으로 구현한 과정

## 한눈에 보기

사내 개발자와 클라이언트 담당자가 함께 쓰는 이슈 관리 시스템입니다. 기존 협업 도구를 대신할 자체 구축안을 제안했고, 승인 이후 애플리케이션 개발을 1인으로 담당했습니다.

2026년 9월 현재 구현과 로컬 시험 이전을 완료했으며, 운영 데이터 대사와 배포를 앞두고 있습니다.

## 문제와 역할

기존에는 클라이언트와의 개발 이슈를 Asana로 관리했습니다. 문제는 비용 하나가 아니라 네 가지가 겹쳐 있었습니다.

- 클라이언트가 기존에 쓰던 협업 도구의 일부 업무 기능이 Asana에는 없었습니다.
- 비개발자 클라이언트에게 범용 도구의 많은 기능과 개념은 학습 부담이 될 수 있었습니다.
- 개인정보와 내부 업무정보를 외부 협업 SaaS에서 주고받는 데 부담이 있었습니다.
- 사용자별 과금은 이용자가 늘수록 반복 비용이 증가했습니다.

Asana와 기존에 검토한 Notion 및 국내 협업 도구를 비교하고, 동료 인터뷰와 클라이언트 피드백을 수집했습니다. 모든 기능을 갖춘 범용 도구보다 이슈 등록·처리·공유라는 핵심 흐름만 제공하고 필요하면 직접 고칠 수 있는 자체 도구가 지금 조직에 맞다고 판단했습니다. 자체 개발에도 비용이 들기 때문에 라이선스 절감액 하나만으로 구축을 정당화하지는 않았습니다.

애플리케이션 개발은 1인이 담당했지만 의사결정과 운영 인프라는 함께 다뤘습니다.

- **본인** — 대안 제안, 요구사항·업무 정책·출시 범위 초안, 기술 구조와 데이터 모델·API·화면 흐름 결정, 프론트엔드·백엔드 구현, 테스트, 이전 도구
- **팀장** — 추진 승인, 요구사항·정책 검토, 운영 배포와 DB 등 외부 인프라 설정

요구사항 변경은 Markdown 명세와 제안서로 먼저 쓰고 승인받은 뒤 반영해, 무엇이 언제 왜 바뀌었는지 남겼습니다.

## 핵심 제품 판단

초기에는 Organization과 Project를 각각 권한 경계로 두고 1차 구현을 진행했습니다. 검토 과정에서 조직 단위 권한이 필요하다는 실제 요구가 없고, 두 계층이 권한 모델과 사용자 화면을 불필요하게 복잡하게 만든다는 점을 확인했습니다.

Organization을 제거하고 Project 하나를 클라이언트별 멤버십·역할·데이터 격리의 유일한 경계로 단순화했습니다. Group은 권한과 무관하게 프로젝트 안에서 이슈를 묶는 선택적 분류로 재정의했습니다.

사용자는 삭제 대신 비활성화를 택했습니다. 사용자 ID가 과거 작성자·담당자·감사 로그 실행자로 참조되므로 물리 삭제는 책임 관계를 훼손하기 때문입니다.

첫 출시 범위도 좁게 잡았습니다. 핵심 흐름과 프로젝트 간 데이터 격리, 실시간 갱신과 알림은 구현과 테스트로 확인했습니다. 기존 데이터를 누락 없이 이전·대사하는 것과 Asana 없이 같은 업무를 수행하는 것은 아직 달성이 아니라 출시 게이트로 관리하고 있습니다.

## 기술적 결정

### 스택은 속도와 익숙함 기준으로

약 두 달 안에 애플리케이션 전반을 혼자 구현해야 했기 때문에 기술 선택의 기준은 속도와 익숙함이었습니다. 프론트엔드와 백엔드 모두 익숙한 TypeScript 생태계를 썼고, 관계형 권한 모델과 트랜잭션이 중요한 업무 시스템이라 PostgreSQL과 Prisma를 선택했습니다.

### 모듈러 모놀리스와 전환 조건

백엔드 구조와 실시간 전달 방식은 하나의 트레이드오프로 함께 정했습니다. 소수 사용자를 위한 단일 API 인스턴스로 충분했으므로, 마이크로서비스와 메시지 브로커 대신 하나의 NestJS 애플리케이션 안에서 도메인 모듈의 경계만 유지했습니다.

대신 전환 조건을 명시적으로 남겼습니다. API 다중 인스턴스가 실제 요구가 되면 인메모리 SSE가 인스턴스 사이의 이벤트를 전달할 수 없으므로, 그 시점에 Redis Pub/Sub 같은 외부 브로커를 도입하도록 문서화했습니다.

### SSE는 데이터가 아니라 신호로

실시간 갱신에서는 SSE를 데이터 채널이 아니라 invalidation signal로만 썼습니다. 업무 데이터의 source of truth는 HTTP API와 DB에 두고, mutation이 커밋되면 SSE로 변경 사실만 알린 뒤 클라이언트가 HTTP로 다시 조회합니다.

실시간 payload와 서버 상태라는 두 개의 상태 모델을 관리하지 않아도 되고, SSE 전달이 실패해도 이미 완료된 저장이 되돌아가지 않습니다. 알림도 같은 흐름 위에 올렸습니다.

### 에이전트 결과를 리뷰로 거르기

에이전트에는 범위가 명확한 구현을 맡기되 요구사항과 완료 조건은 직접 정의하고, 리뷰·통합·최종 승인은 직접 판단했습니다. 아키텍처 대안을 추천받기도 했지만 일정과 운영 조건을 검토해 최종 구조는 직접 결정했습니다.

한 번은 에이전트가 SSE 발행을 DB 트랜잭션 안에 배치해, 실시간 전달 실패가 핵심 업무 저장까지 실패시킬 수 있는 구현을 만들었습니다. 운영 장애가 아니라 병합 전 독립 코드 리뷰에서 발견해, DB 변경을 먼저 커밋하고 SSE는 이후 best-effort로 발행하도록 경계를 옮겼습니다.

## 테스트와 데이터 이전

단위·통합·실제 PostgreSQL 기반 API E2E 테스트의 라인 커버리지 90% 이상을 품질 기준으로 두고, 로그인부터 이슈 등록·담당자 지정·댓글·첨부·실시간 갱신까지 주요 사용자 시나리오를 Playwright E2E로 검증했습니다. 다른 프로젝트의 ID로 접근했을 때 실제로 거부되는지도 API E2E로 확인해, 데이터 격리가 화면이 아니라 API 계층에서 지켜지도록 했습니다.

기존 시스템을 실제로 교체하려면 제품 구현만으로는 부족했습니다. Asana의 사용자·이슈·댓글·첨부파일을 옮기는 이전 도구를 함께 만들고, 로컬에서 이슈 약 500건·댓글 약 900건·첨부 약 400건 규모로 시험 이전했습니다.

원본 GID와 신규 ID의 매핑을 별도로 보존해 같은 원본을 다시 실행해도 중복이 생기지 않고, 실패 경계를 Task 하나로 좁혀 한 건이 실패해도 나머지 이전은 계속됩니다. 첨부파일은 외부 I/O를 트랜잭션 밖에서 먼저 처리하고, 이후 DB 트랜잭션이 실패하면 미리 저장한 파일을 보상 삭제합니다.

## 현재 결과와 회고

약 두 달 동안 요구사항 정의와 제품·기술 설계부터 풀스택 구현, 테스트, 시험 이전까지 담당해 운영 대사와 배포가 가능한 상태로 만들었습니다. 실사용 결과는 배포 이후에 확인할 수 있습니다.

처음에는 클라이언트별 Organization 계층이 당연히 필요하다고 생각했습니다. 실제 권한 요구를 검토하자 Project 하나로 충분했고, 계층이 적은 편이 사용자에게도 이해하기 쉬웠습니다. 다시 시작한다면 익숙한 도메인 구조를 먼저 모델링하지 않고, 누가 어떤 데이터에 어떤 행동을 해야 하는지부터 검증하겠습니다.

확장 가능한 구조도 모든 복잡성을 미리 구현하는 것이 아니라, 복잡성을 추가할 조건을 분명히 아는 것이라는 점을 배웠습니다. 지표를 정할 때도 같은 기준을 적용했습니다. 이슈 처리시간은 이슈 난이도와 담당자 업무량의 영향이 커서 시스템의 성과로 쓰지 않기로 했습니다.
