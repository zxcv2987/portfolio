> 편집 원칙: 확인되지 않은 수치와 아직 달성하지 않은 운영 성과를 완료형으로 쓰지 않는다.

## 0. 작업자 실행 지침

이 문서만 작업 기준으로 사용해 현재 Astro 포트폴리오에 콘텐츠 개편을 실제 반영한다.
추가 설명을 기다리지 말고 저장소를 먼저 확인한 뒤 합리적인 범위에서 끝까지 구현한다.

작업 순서:

1. 루트 `AGENTS.md`와 수정 대상 파일을 읽는다.
2. `git status --short`와 `git diff`로 기존 사용자 변경을 확인한다.
3. 아래 사실 관계와 편집 기준에 따라 Markdown 및 필요한 Astro 코드를 수정한다.
4. 기존 디자인 시스템과 콘텐츠 로딩 구조를 유지한다.
5. `package.json`의 scripts를 확인하고 관련 format, lint, typecheck, test, build를 실행한다.
6. 실패한 검증은 원인과 함께 보고하며, 무관한 오류를 고치기 위해 작업 범위를 넓히지 않는다.
7. 최종 보고에는 수정한 파일, 핵심 콘텐츠 결정, 실행한 검증과 남은 공개 전 확인사항을 적는다.

반드시 지킬 제한:

- 기존 변경을 reset, checkout, stash, 삭제하거나 덮어쓰지 않는다.
- 사실을 새로 추정하지 않는다. 이 문서에서 미확인으로 표시한 값은 미확인 상태로 둔다.
- 운영 대사·배포·실사용 성과를 완료형으로 바꾸지 않는다.
- 실제 회사·클라이언트 데이터가 담긴 화면 캡처를 추가하지 않는다.
- 단지 문서의 예시 문장을 복사하는 데 그치지 말고, 기존 페이지의 문체와 정보 밀도에 맞춰
  중복을 제거한 완성도 높은 한국어 콘텐츠로 편집한다.
- 범위 안의 안전한 판단은 직접 내린다. 사실 확인이 필요한 경우에만 작업을 멈추고 질문한다.

## 1. 이번 개편의 목표

포트폴리오의 중심 인상을 다음 문장으로 통일한다.

> 사용자 문제를 이해하고 더 나은 제품 경험을 만들어가는 프론트엔드 엔지니어

지원 직무는 프론트엔드 엔지니어와 프로덕트 엔지니어다. 회사 규모나 산업은 제한하지
않는다. 따라서 특정 스타트업 문화에만 맞는 과도한 오너십 표현이나, 반대로 화면 구현에만
역할을 한정하는 표현을 피한다.

Carrier 사례는 다음 역량을 증명해야 한다.

> 모호한 내부 요구를 사용자 인터뷰와 기존 도구 분석을 통해 제품 정책으로 구체화하고,
> 일정·사용자 규모·운영 조건에 맞는 기술 구조를 선택해 출시 가능한 제품으로 완성하는 역량

기술 스택과 AI 에이전트 사용은 주제가 아니라 이 역량을 뒷받침하는 근거로만 사용한다.

## 2. 사실 관계와 표현 경계

### 공개 가능한 사실

- 2026년 7월 착수. 정확한 날짜는 검증하지 못했으므로 `2026.07`까지만 표기한다.
- 지속적으로 구현한 개발자는 본인 1명이다.
- 본인이 요구사항 구체화, 업무 정책 초안, 출시 범위 제안, 기술 설계, 화면 흐름, 데이터
  모델, API, 프론트엔드·백엔드 구현, 로컬 Docker 환경, 테스트와 이전 도구를 담당했다.
- 팀장은 추진 방향과 요구사항을 검토·승인하고 운영 배포·DB 등 외부 인프라를 설정했다.
- 사용자는 복수의 사내 개발자와 복수의 클라이언트 담당자다.
- 기술 스택, 일반화한 업무 흐름, 아키텍처·데이터 모델, 대략적인 이전 규모는 공개 가능하다.
- 회사명과 클라이언트명은 비식별화한다. 실제 업무 데이터가 보이는 화면 캡처는 사용하지
  않는다.

### 표현하면 안 되는 내용

- `2026년 7월 20일` 또는 `7월 27일`처럼 검증되지 않은 정확한 착수일
- 운영 배포, 최종 대사, Asana 대체, 실사용이 이미 완료됐다는 표현
- 운영 장애를 경험했다고 읽히는 표현. SSE·쿼리 키 문제는 리뷰에서 운영 전에 발견했다.
- 운영 인프라 설정과 배포 전체를 본인이 했다는 표현
- 아키텍처를 아무런 도움 없이 처음부터 독자적으로 고안했다는 표현
- 모든 커버리지 지표가 90% 이상이라는 표현. `라인 커버리지 90% 이상`으로 한정한다.
- Asana 비용 절감액을 확정 성과로 제시하는 표현
- 외부 SaaS에서 개인정보 유출이 실제 발생했다는 표현

### AI 에이전트 역할 표현

다음 경계를 유지한다.

> 요구사항과 제약조건, 구현 단계와 완료 조건은 본인이 정의했다. 아키텍처 대안은
> 에이전트에게 추천받기도 했으며, 일정·복잡도·운영 조건을 검토해 최종 구조를 본인이
> 결정했다. 범위가 명확한 구현을 에이전트에 맡기고 코드 리뷰, 통합, 테스트와 최종 승인
> 여부를 직접 판단했다.

`AI로 빠르게 만들었다`보다 `생성된 결과를 검증 가능한 개발 흐름 안에서 관리했다`를
강조한다.

## 4. 프로필 문구

메인 헤드라인을 다음으로 변경한다.

> 사용자 문제를 이해하고 더 나은 제품 경험을 만들어가는 프론트엔드 엔지니어

보조 소개 문구는 다음 의미를 담되, 문장이 길면 두 문장으로 나눈다.

> 실제 사용자 환경에서 발생한 문제를 데이터로 추적하고, 복잡한 업무 흐름을 이해하기
> 쉬운 제품 경험으로 구체화합니다. 프론트엔드를 중심으로 일하지만 필요한 경우 API,
> 권한, 실시간 처리와 데이터 이전까지 제품의 완성에 필요한 경계를 함께 다룹니다.

`설계부터 출시까지 주도하는`, `제품 전체를 책임지는`처럼 1년차 소개 문구로 지나치게
무거운 자기 규정은 피한다. 구체적인 오너십은 각 사례 안에서 사실로 증명한다.

## 5. Carrier 상세 사례 최종 구성

### Frontmatter 권장안

```yaml
title: "사내 이슈 관리 시스템을 요구사항부터 풀스택으로 구현한 과정"
slug: "carrier"
category: "Work Experience · 0→1 Product"
company: "주식회사 팀마파"
period: "2026.07 - 현재"
role: "Frontend Engineer · Sole Application Developer"
summary: "기존 협업 도구의 업무 적합성·민감정보·인당 과금 문제를 바탕으로 요구사항과 정책을 구체화하고, 이슈 관리 제품의 설계·풀스택 구현·테스트·Asana 이전 준비를 담당했습니다."
featured: true
order: 1
```

`Sole Application Developer`가 사이트 전체의 한국어 톤과 맞지 않으면 `애플리케이션 개발
1인 담당`으로 바꾼다. 외부 인프라까지 단독 담당했다는 오해가 없도록 본문 담당 범위에서
팀장 역할을 명시한다.

권장 highlights:

- `요구사항·제품 정책부터 풀스택 구현까지 1인 담당`
- `단위·통합·API E2E 라인 커버리지 90% 이상`
- `이슈 약 500건·댓글 약 900건·첨부 약 400건 시험 이전`

마지막 수치는 기억에 따른 대략값이므로 반드시 `약`을 붙인다. 더 보수적으로 쓰려면
`수백 건 규모의 이슈·댓글·첨부 시험 이전`으로 바꾼다.

### 5.1 한눈에 보기

첫 문단은 문제, 역할, 현재 결과를 한 번에 보여준다.

> 사내 개발자와 클라이언트 담당자가 함께 사용하는 이슈 관리 시스템을 만들었습니다.
> 기존 협업 도구의 업무 적합성, 민감한 정보 취급, 사용자 증가에 따라 반복되는 인당 과금
> 구조를 검토한 뒤 자체 구축안을 제안했습니다. 승인 이후 요구사항과 제품 정책을
> 구체화하고 프론트엔드·백엔드와 데이터 이전 도구까지 애플리케이션 개발을 1인으로
> 담당했습니다.

현재 상태는 별도 문장으로 분명히 한다.

> 2026년 9월 현재 구현과 로컬 시험 이전을 완료했으며, 운영 데이터 대사와 배포를 앞두고
> 있습니다.

### 5.2 문제와 자체 구축 판단

문제는 비용 하나로 설명하지 않는다.

- 클라이언트가 기존에 사용하던 협업 도구의 일부 업무 기능이 Asana에는 없었다.
- 비개발자 클라이언트에게 범용 도구의 많은 기능과 개념은 학습 부담이 될 수 있었다.
- 개인정보와 내부 업무정보를 외부 협업 SaaS에서 주고받는 데 부담이 있었다.
- 사용자별 과금은 이용자가 늘수록 반복 비용이 증가했다.

Asana Starter 10석의 현재 공개 가격을 계산한 값은 내부 근거로만 유지하고 본문에는 정확한
절감액을 넣지 않는다. 자체 개발 비용을 고려하면 비용 하나만으로 구축을 정당화하기 어렵기
때문이다.

대안 검토는 다음처럼 쓴다.

> Asana와 기존에 검토한 Notion 및 국내 협업 도구를 비교하고, 동료 인터뷰와 클라이언트
> 피드백을 수집했습니다. 모든 기능을 제공하는 범용 도구보다 이슈 등록·처리·공유라는 핵심
> 흐름만 제공하고 필요에 따라 직접 수정할 수 있는 자체 도구가 현재 조직에 적합하다고
> 판단했습니다.

특정 국내 도구 이름은 공개하지 않는다.

### 5.3 핵심 사용자 흐름과 성공 조건

핵심 흐름:

```text
클라이언트가 이슈 등록
→ 개발자가 담당자·상태·우선순위 지정
→ 댓글과 첨부파일로 진행 상황 공유
→ 실시간 갱신과 알림으로 변경 확인
→ 완료 또는 재개
```

첫 출시 완료 조건:

- 위 핵심 흐름을 사용자가 수행할 수 있다.
- 클라이언트별 프로젝트 데이터가 섞이지 않는다.
- 변경 내용이 실시간 갱신과 인앱·브라우저 알림으로 전달된다.
- 기존 이슈·댓글·첨부파일을 누락 없이 이전하고 대사할 수 있다.
- 이전과 운영 검수 후 Asana 없이 같은 업무를 수행할 수 있다.

현재는 마지막 두 항목의 운영 검수가 남았으므로 `달성했다`가 아니라 `출시 게이트로
정의했다`고 쓴다.

### 5.4 역할과 협업 방식

역할을 표로 명확히 나눈다.

| 구분 | 담당 |
| --- | --- |
| 본인 | 대안 제안, 요구사항 구체화, 업무 정책·출시 범위 초안, 기술 구조·데이터 모델·API·화면 흐름 결정, 풀스택 구현, 로컬 Docker, 테스트, 이전 도구 |
| 팀장 | 추진 승인, 요구사항·정책 검토, 운영 배포·DB 등 외부 인프라 설정 |
| 동료·클라이언트 | 기존 도구와 업무 흐름에 대한 인터뷰·피드백 제공 |

요구사항 변경은 Markdown 명세와 제안서로 먼저 작성하고, 대화·회의에서 승인받은 뒤 내용을
반영하고 수정일을 기록했다.

### 5.5 제품 모델 단순화

Organization 제거 사례를 중심으로 구성한다.

> 초기에는 Organization과 Project를 각각 권한 경계로 두고 1차 구현을 진행했습니다.
> 검토 과정에서 조직 단위 권한이 필요하다는 실제 요구가 없고, 두 계층이 권한 모델과
> 사용자 화면을 불필요하게 복잡하게 만든다는 점을 확인했습니다. Organization을 제거하고
> Project 하나를 클라이언트별 멤버십·역할·데이터 격리의 유일한 경계로 단순화했습니다.
> Group은 권한과 무관하게 프로젝트 안에서 이슈를 묶는 선택적 분류로 재정의했습니다.

사용자 비활성화 정책:

> 사용자 ID가 과거 이슈 작성자·담당자·댓글 작성자·감사 로그 실행자로 참조되므로 물리
> 삭제는 책임 관계를 훼손할 수 있습니다. 계정과 멤버십은 비활성화하되 과거 이력은
> 보존하고, 개인정보 삭제가 필요하면 행 삭제가 아닌 식별정보 익명화를 후속 정책으로
> 검토하도록 했습니다.

### 5.6 기술 선택과 확장 조건

기술 선택 기준은 `속도와 익숙함`이다.

> 약 두 달 안에 혼자 제품 전반을 구현해야 했기 때문에 익숙한 TypeScript 생태계를
> 프론트엔드와 백엔드에 사용했습니다. React/Vite와 NestJS로 전환 비용을 줄였고,
> 관계형 권한 모델과 트랜잭션이 중요한 업무 시스템이라 PostgreSQL과 Prisma를
> 선택했습니다.

검토하지 않은 기술 대안과 비교했다고 쓰지 않는다.

모듈러 모놀리스와 단일 인스턴스 SSE는 하나의 트레이드오프로 묶는다.

> 현재는 소수 사용자를 위한 단일 API 인스턴스로 충분했습니다. 초기부터 마이크로서비스와
> 메시지 브로커를 도입하지 않고, 하나의 NestJS 애플리케이션 안에서 도메인 모듈의 경계를
> 유지했습니다. API 다중 인스턴스와 로드밸런싱이 실제 요구가 되면 인메모리 SSE가
> 인스턴스 사이의 이벤트를 전달할 수 없으므로 Redis Pub/Sub 같은 외부 브로커를 도입하는
> 것을 명시적인 전환 조건으로 남겼습니다.

### 5.7 실시간 일관성과 알림

HTTP/DB를 source of truth로 유지하고 SSE는 invalidation signal로만 사용한 이유를 설명한다.

```text
사용자 mutation
→ DB transaction commit
→ SSE로 projection/대상 invalidation 신호 발행
→ TanStack Query cache 무효화
→ HTTP로 최신 서버 상태 재조회
```

강조할 판단:

- 실시간 payload와 서버 상태라는 두 상태 모델을 관리하지 않는다.
- 중복·역순 이벤트는 추가 재조회로 흡수한다.
- 재연결 시 활성 쿼리를 일괄 무효화해 누락을 보정한다.
- SSE 실패가 이미 완료된 업무 저장을 되돌리지 않는다.

알림은 행위자와 비활성 사용자를 제외하고 멘션·구독 등 수신 근거가 겹치면 중복을 제거한다.
인앱 알림을 저장한 뒤 사용자 단위 실시간 이벤트를 보내며 브라우저 알림은 권한이 있을 때만
표시한다.

### 5.8 권한과 데이터 격리

> 인증으로 사용자 신원을 확인한 뒤 모든 보호 API에서 활성 프로젝트 멤버십과 역할을
> 검사했습니다. 같은 프로젝트 경계를 이슈·댓글·첨부파일과 실시간 구독에 일관되게
> 적용했습니다. 다른 프로젝트의 ID를 사용한 접근이 거부되는지 실제 PostgreSQL 기반 API
> E2E 테스트로 검증했습니다.

권한 모델 그림을 추가한다면 `User → ProjectMembership → Project → Issue/Comment/Attachment`
관계만 보여준다. Group은 Issue의 선택적 분류로 옆에 배치하고 권한선과 연결하지 않는다.

### 5.9 에이전트 활용과 리뷰 사례

에이전트 관련 내용은 한 섹션 이내로 제한한다. 대표 결함은 SSE 트랜잭션 경계를 사용한다.

> 에이전트가 SSE 발행을 DB 트랜잭션 안에 배치해, 실시간 전달 실패가 핵심 업무 저장까지
> 실패시킬 수 있는 구현을 만든 적이 있습니다. 리뷰에서 이를 발견해 DB 변경을 먼저
> 커밋하고 SSE는 이후 best-effort로 발행하도록 경계를 수정했습니다.

보조 사례:

- 쿼리 키 팩토리를 누락하고 하드코딩한 부분을 리뷰에서 발견해 기존 규칙으로 통일
- 한 파일이 800~900줄 이상 커진 부분을 책임별로 분리하는 중간 리팩터링 수행

이 사례들은 운영 장애가 아니라 코드 리뷰 단계에서 발견해 수정한 것으로 쓴다. `phase-review`
같은 내부 스킬 이름은 독자에게 맥락이 없으므로 본문에서는 `독립 코드 리뷰` 정도로
일반화한다.

### 5.10 테스트 전략

요약 문구:

> 단위·통합·실제 PostgreSQL 기반 API E2E 테스트의 라인 커버리지 90% 이상을 품질 기준으로
> 두고, 로그인부터 이슈 등록·담당자 지정·댓글·첨부·권한 분리·실시간 갱신까지 주요 사용자
> 시나리오를 Playwright E2E로 검증했습니다.

커버리지와 E2E 역할을 구분한다.

- 커버리지: 코드 경로의 회귀 방지 기반
- API E2E: 실제 DB 제약, 트랜잭션, 프로젝트 권한 경계 검증
- Playwright E2E: 사용자가 수행하는 핵심 업무 흐름 검증

현재 저장소 문서의 테스트 파일 수나 세부 커버리지는 시점에 따라 바뀔 수 있으므로, 화면에
정적 숫자로 넣으려면 빌드 시점에 다시 확인한다. 브랜치 커버리지 90% 이상이라고 쓰지 않는다.

### 5.11 Asana 이전

대략적인 시험 데이터 규모:

- 이슈 약 500건
- 댓글 약 900건
- 첨부파일 약 400건

정확한 원본 보고서가 없으면 `수백 건 규모`로 낮춰 써도 된다.

파이프라인:

```text
Asana API
→ 리소스별 원본 snapshot(jsonb upsert)
→ 매핑 후보와 정적 매핑표 검증
→ dry-run
→ Task 단위 Import
→ 원본/성공/제외/실패 대사
→ 표본 검수와 승인
```

멱등성:

- 원본 snapshot은 workspace GID와 원본 GID로 upsert한다.
- 별도 매핑 테이블이 `workspace + resourceType + sourceGid → Carrier ID`를 보존한다.
- 매핑이 있으면 기존 리소스를 update하고 없을 때만 create한다.
- 같은 snapshot 재실행 시 중복이 생기지 않는다.

부분 실패:

- Task와 관련 담당자·댓글·첨부를 Task 단위 트랜잭션으로 처리한다.
- 하나가 실패하면 해당 Task만 롤백하고 다른 Task는 계속 진행한다.
- 실패 Task GID를 수집하고 하나라도 실패하면 CLI 종료 코드 1을 반환한다.
- 원본 Task·댓글·첨부 수와 성공 매핑·정책상 제외 수를 대사한다.

첨부 보상 처리:

> 2분만 유효한 Asana 다운로드 URL과 스토리지 쓰기를 DB 트랜잭션 밖에서 먼저 처리해
> 트랜잭션이 외부 I/O를 기다리지 않게 했습니다. 이후 DB 트랜잭션이 실패하면 미리 저장한
> 파일을 보상 삭제해 고아 파일이 남지 않도록 했습니다.

### 5.12 현재 결과와 출시 후 지표

현재 결과:

> 약 두 달 동안 요구사항 정의와 제품·기술 설계부터 풀스택 구현까지 담당하고,
> 단위·통합·API E2E 테스트의 라인 커버리지 90% 이상과 주요 사용자 시나리오 E2E를
> 구축했습니다. 수백 건 규모 데이터의 로컬 시험 이전까지 완료해 운영 대사와 배포가
> 가능한 상태로 만들었습니다.

운영 전환 전까지 결과 제목은 `현재 결과` 또는 `출시 준비 상태`로 둔다. `성과`라는 제목은
실사용 결과가 생긴 뒤 사용한다.

배포 후 갱신할 지표:

- 원본 대비 이슈·댓글·첨부 대사 결과
- 데이터 누락 건수
- 프로젝트 간 정보 노출 등 권한 사고 건수
- 업무를 중단시키는 치명적 운영 장애 건수
- 보조: 알림 누락·중복, 배포 후 발견·수정한 결함, 사용자 정성 피드백

이슈 처리시간은 이슈 난이도와 담당자 업무량의 영향을 크게 받아 시스템 성과로 사용하지
않는다. 신규 이슈 전환율도 Asana 종료 정책에 의해 결정되므로 품질 지표가 아니라 출시
완료 조건으로만 다룬다.

### 5.13 회고

두 가지 학습을 남긴다.

1. 미래 확장성은 실제 전환 조건과 함께 미룰 수 있다.
2. 도메인 모델을 만들기 전에 실제 사용자에게 필요한 권한 단위를 먼저 검증해야 한다.

권장 문안:

> 처음에는 클라이언트별 Organization 계층이 당연히 필요하다고 생각했습니다. 하지만 실제
> 권한 요구를 검토하자 Project 하나로 충분했고, 계층이 적은 편이 사용자에게도 더
> 이해하기 쉬웠습니다. 다시 시작한다면 익숙한 도메인 구조를 먼저 모델링하지 않고, 누가
> 어떤 데이터에 어떤 행동을 해야 하는지부터 검증하겠습니다.
>
> 실시간 통신과 백엔드 구조도 현재 규모에 필요한 단순성에서 시작했습니다. 단일 인스턴스
> SSE와 모듈러 모놀리스를 선택하되 다중 인스턴스가 필요한 시점을 확장 조건으로
> 문서화했습니다. 확장 가능한 구조는 모든 복잡성을 미리 구현하는 것이 아니라, 복잡성을
> 추가할 조건을 분명히 아는 것이라는 점을 배웠습니다.

## 6. 관리자 리뉴얼 편집 기준

현재 사례의 핵심은 유지한다.

- Next.js 주요 기능을 사용하지 않는 관리자 SPA의 실제 요구 분석
- Vite 전환
- 빌드 시간 약 10분에서 약 30초
- 라우팅·권한·데이터 요청·공통 UI의 변경 경계 정리

Carrier와 겹치는 다음 표현은 줄인다.

- 제품 요구사항 전체를 정의했다는 장황한 설명
- 풀스택 또는 출시 전체 오너십
- TanStack Query 자체에 대한 반복 설명

제목과 요약에서 `Vite 전환`과 `개발 피드백 시간 단축`이 바로 드러나게 한다. 빌드 측정
조건이 아직 공개 전 확인 항목이라면 정확한 수치는 유지하되 `측정 환경 기준`을 보완하거나
검증 전임을 주석에 남긴다.

## 7. 기기 판별 사례 편집 기준

이 사례는 짧고 선명하게 유지한다.

```text
갤럭시 태블릿의 데스크톱 모드가 Linux PC로 오인
→ 원격 지원과 Sentry 환경 데이터로 원인 확인
→ User-Agent 단일 판별의 한계 정의
→ 화면·터치·GPU 등 복수 신호 휴리스틱 적용

```

검증하지 않은 탐지율이나 장애 감소율은 만들지 않는다. 실제 환경 데이터로 진단한 과정과
단일 신호의 한계를 보완한 판단을 강점으로 둔다.

권장 요약:

> 초기에는 학생용 앱을 담당했고, 이후 사용자·관리자 앱과 공통 모듈을 Turborepo로 단독
> 통합했습니다. 직접 배포한 뒤 프론트엔드 유지보수와 기능 개선을 전담하며 캐시 무효화,

`현재 프론트엔드 저장소에는 내 커밋밖에 없다`는 문장은 검증 가능한 기여 범위를 설명하는
내부 근거로만 사용한다. 공개 문장에서는 `출시 후 전담`으로 충분하다.

## 9. 시각자료 원칙

Carrier의 실제 화면 캡처는 필수가 아니며 기본적으로 제외한다. 다음 두 도식만 우선한다.

1. 실시간 데이터 흐름: `mutation → commit → SSE invalidation → query invalidate → HTTP refetch`
2. 이전 파이프라인: `snapshot → mapping → task transaction → reconcile`, 실패 시 첨부 보상 삭제

선택적으로 권한 모델 도식을 추가한다. 모든 도식은 현재 사이트의 기존 디자인 토큰과 Astro
컴포넌트 패턴을 재사용하고, 모바일에서 가로 스크롤 없이 읽혀야 한다. 장식 목적의 거대한
그래픽은 만들지 않는다.

현재 작업 트리는 이미 수정 상태다. 작업자는 다음을 지켜야 한다.

- 기존 사용자 변경을 reset, checkout, stash, 삭제하지 않는다.
- 수정 전 `git diff`로 겹치는 내용을 확인한다.
- 본 명세와 직접 관련된 부분만 최소 범위로 편집한다.
- `carrier.md`와 인터뷰 계획은 새 파일일 수 있으므로 추적 여부를 이유로 삭제하지 않는다.
- 정확한 수치를 새로 추정하거나 사실을 보완해서 만들지 않는다.

### 콘텐츠 검수

- 착수 시점은 `2026.07`로 표시됐는가?
- 운영 대사·배포를 완료형으로 쓰지 않았는가?
- 본인과 팀장의 역할 경계가 명확한가?
- AI가 아키텍처 대안을 제시했고 최종 판단·검증은 본인이 했다는 경계가 정확한가?
- SSE 결함이 운영 장애가 아니라 리뷰 단계 발견으로 표현됐는가?
- 테스트 수치는 라인 커버리지 90% 이상으로 한정됐는가?
- 이전 데이터 숫자에 `약`이 붙었는가?
- 관리자 리뉴얼과 Carrier의 핵심 메시지가 겹치지 않는가?
- 동글의 초기 팀 기여와 출시 후 단독 운영이 시점별로 구분됐는가?

### 기술 검수

- 기존 Astro 콘텐츠 로딩 방식과 frontmatter schema를 깨지 않는다.
- `pnpm` 프로젝트의 기존 lint, typecheck, test, build 명령을 package scripts에서 확인해
  관련 검증을 실행한다.
- 새 도식은 키보드 탐색, 색상 대비, 모바일 레이아웃을 확인한다.
- 실패한 검증은 숨기지 않고 명령과 오류를 최종 보고에 포함한다.
